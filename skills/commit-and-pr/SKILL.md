# commit-and-pr

현재 변경점을 커밋하고 PR을 만드는 데까지 한 번에 진행한다. 커밋과 PR 생성 직전에 사용자 확인을 받는다.

## 언제 쓰나

- "커밋하고 PR 올려줘", "ship", "PR 만들어줘"라고 요청받았을 때
- 작업을 마치고 변경점을 브랜치로 올려 리뷰를 받으려 할 때

## 입력

| 항목 | 기본값 | 설명 |
| --- | --- | --- |
| 대상 브랜치 (`--base`) | 저장소 기본 브랜치 | PR을 보낼 브랜치 |
| 커밋 type (`--type`) | 변경 성격에서 추론 | feat, fix, chore, refactor, docs, design 중 하나 |
| 커밋 메시지 (`--message`) | 변경점에서 작성 | 직접 지정하면 메시지 확인 단계를 건너뛴다 |
| 브랜치 이름 (`--branch`) | 변경 내용에서 제안 | 새 브랜치가 필요할 때 사용 |
| Draft (`--draft`) | 아니오 | Draft PR로 만든다 |

## 원칙

- 저장소에 자체 git 규칙(예: `CLAUDE.md`, `.agent/rules/git.md`)이 있으면 그것을 먼저 읽고 우선한다. 이 문서는 규칙이 없을 때의 기본값이다.
- 아래 두 시점에는 반드시 사용자 확인을 받고 진행한다.
  - 커밋 전: 커밋 메시지
  - PR 생성 전: PR 제목과 본문
- 기본 브랜치(`main`, `master`)에 직접 커밋하거나 push하지 않는다. 항상 브랜치를 거쳐 PR로 올린다.
- 사용자가 명시적으로 요청하지 않는 한 `git push --force`, `git commit --no-verify`, 공유 브랜치의 `git reset --hard`는 쓰지 않는다.
- `.env`, 자격증명, 시크릿이 들어 있는 파일은 커밋하지 않는다.

## 절차

1. 변경점을 확인한다.
   - `git status --short`와 `git diff --stat`을 실행한다.
   - 변경이 없으면 "커밋할 변경점이 없다"고 알리고 중단한다.
   - 민감 파일이 있으면 커밋 전에 경고한다.
   - 변경 파일 목록과 요약을 사용자에게 보여준다.
2. 브랜치를 정한다.
   - 현재 브랜치가 기본 브랜치이면 새 브랜치를 만든다. 변경 내용에서 이름을 제안하고 사용자에게 확인받는다.
   - 이미 작업 브랜치이면 그대로 쓴다.
3. 커밋 메시지를 작성하고 확인받는다. 승인 전에는 커밋하지 않는다.
4. 요청 범위의 파일만 스테이징하고 커밋한다. 무관한 변경은 포함하지 않는다.
5. 원격에 push한다. 처음이면 `git push -u origin <브랜치>`를 쓴다.
6. PR 제목과 본문을 작성하고 확인받은 뒤 만든다.
   `gh pr create --base <대상 브랜치> --title "<제목>" --body "<본문>"`
7. 저장소에 라벨이나 담당자 규칙이 있으면 적용한다. 없는 라벨을 새로 만들지 않는다.
8. 결과를 보고한다.

## 브랜치 이름

| 접두사 | 용도 |
| --- | --- |
| `feat/<kebab-description>` | 새 기능 |
| `fix/<kebab-description>` | 버그 수정 |
| `chore/<kebab-description>` | 설정, 도구, 문서 |
| `refactor/<kebab-description>` | 동작 변경 없는 구조 개선 |

항상 최신 기본 브랜치에서 분기한다.

## 커밋 메시지

```
{type}({scope}): {요약}

{변경 이유. 비자명한 경우에만}
```

- type은 feat, fix, chore, refactor, docs, design 중에서 고른다.
- scope는 변경된 주요 디렉터리나 앱 이름이다.
- 제목은 50자 안팎으로 쓰고, 무엇을 했는지보다 왜 했는지가 드러나게 쓴다.
- 서로 관련 없는 변경은 같은 커밋에 넣지 않는다. 여러 개면 커밋을 나눈다.
- 공동 작성자(Co-Authored-By) 줄이 필요하면 사용 중인 환경의 지침을 따른다.

## PR 본문

```markdown
## 개요

변경 목적을 1~3줄로 쓴다.

## 변경 내용

- 주요 변경 항목

## 테스트

- [ ] 로컬 실행 확인
- [ ] 주요 흐름 확인
```

- 본문은 `git log <대상 브랜치>..HEAD --oneline`과 `git diff <대상 브랜치>...HEAD --stat`을 읽고 작성한다.
- 실제로 실행하지 않은 테스트를 체크된 항목으로 쓰지 않는다.

## 보고 형식

- 브랜치: 이름과 대상 브랜치
- 커밋: 짧은 SHA와 제목
- PR: URL과 제목
- 건너뛴 단계가 있으면 이유와 함께 밝힌다.

## 주의

- 사용자가 승인하지 않은 메시지나 본문으로 진행하지 않는다.
- PR 생성 후 merge는 이 Skill의 범위가 아니다. 사용자가 요청할 때만 진행한다.
- push나 PR 생성이 실패하면(권한, 원격 없음 등) 원인을 그대로 알리고 임의로 우회하지 않는다.
