# pr-list

GitHub에 로그인된 계정이 기간 안에 머지한 PR을 전체 저장소에서 모아, PR 제목을 기준으로 "어떤 활동을 했는가"를 한눈에 보이게 정리한다. 모든 항목에 건수, 변경 규모 같은 숫자 근거를 붙인다.

## 언제 쓰나

- "이번 주 PR 정리해줘", "2026년 상반기에 내가 한 일 PR로 정리해줘"처럼 특정 기간의 활동을 PR로 보고 싶을 때
- 주간·월간·반기 회고, 성과 정리, 이력 작성의 근거 자료가 필요할 때

## 입력: 기간 (4가지 중 선택)

기간이 주어지지 않으면 아래 4가지 중 어느 것인지 먼저 묻는다.

| 선택 | 범위 | 예 |
| --- | --- | --- |
| 이번 주 | 이번 주 월요일 ~ 일요일 | 오늘이 2026-09-19(토)이면 2026-09-14 ~ 2026-09-20 |
| 이번 달 | 이번 달 1일 ~ 말일 | 2026-09-01 ~ 2026-09-30 |
| 특정 월 | 지정한 달의 1일 ~ 말일. 연도를 생략하면 올해 | "2026년 3월" → 2026-03-01 ~ 2026-03-31 |
| 자유 입력 | 사용자가 쓴 기간을 시작일과 종료일로 바꾼다 | "2026년" → 01-01 ~ 12-31, "2026년 1월~3월" → 01-01 ~ 03-31, "2026년 상반기" → 01-01 ~ 06-30 |

- 자유 입력은 "하반기"(07-01 ~ 12-31), "분기"(1분기 01-01 ~ 03-31 등)도 같은 방식으로 바꾼다.
- 기간을 날짜로 바꾼 뒤 결과 첫 줄에 `YYYY-MM-DD ~ YYYY-MM-DD`로 밝힌다. 해석이 애매하면(예: "작년 말") 추측하지 말고 날짜를 확인받는다.
- 종료일이 오늘보다 미래이면 오늘까지의 결과임을 밝힌다.

## 입력: 대상

- 계정: 현재 `gh`에 로그인된 계정. `gh api user --jq .login`으로 확인한다. 다른 계정을 원하면 사용자가 지정한다.
- 저장소: 그 계정이 작성한 PR이 있는 모든 저장소(개인 저장소와 소속 조직 저장소). 비공개(private) 저장소도 포함한다. 저장소를 따로 좁히지 않는다.
- 비공개 저장소 조회에는 `gh` 토큰에 `repo` 권한이 필요하다. `gh auth status`의 Token scopes에 `repo`가 없으면 공개 저장소만 조회되므로 그 사실을 밝히고 `gh auth refresh -s repo`를 안내한다.
- 기준: 기간 안에 머지된 PR. 머지되지 않은 PR(오픈, 닫힘)은 포함하지 않는다.

## 절차

1. `gh auth status`로 로그인 여부를 확인한다. 로그인되어 있지 않으면 진행하지 말고 `gh auth login`을 안내한다.
2. 로그인 계정 이름을 가져온다.
3. GraphQL 검색으로 기간 안에 머지한 PR을 모두 가져온다. 변경 규모(추가·삭제 줄, 변경 파일 수)는 검색 결과에 포함된다.

   ```bash
   gh api graphql --paginate -f q="author:USER is:pr is:merged merged:START..END" -f query='
   query($q: String!, $endCursor: String) {
     search(query: $q, type: ISSUE, first: 100, after: $endCursor) {
       issueCount
       pageInfo { hasNextPage endCursor }
       nodes { ... on PullRequest {
         number title url mergedAt additions deletions changedFiles
         repository { nameWithOwner isPrivate }
       } }
     }
   }'
   ```

4. GitHub 검색은 한 쿼리에 최대 1,000건까지 돌려준다. `issueCount`가 1,000을 넘으면 기간을 월 단위로 쪼개 여러 번 조회한 뒤 합친다.
5. PR 제목을 기준으로 활동 유형으로 분류한다.
   - 제목이 `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `perf`, `ci` 같은 접두사로 시작하면 그것을 따른다.
   - 접두사가 없으면 제목의 내용으로 판단해 가장 가까운 유형에 넣는다. 판단이 어려우면 "기타"로 둔다.
6. 아래 출력 형식으로 작성한다.

## 출력 형식

위에서부터 순서대로 쓴다. 가장 중요한 "주요 활동"을 맨 위에 두고, 조회 정보는 맨 아래에 둔다.

```markdown
# PR 리스트업 (YYYY-MM-DD ~ YYYY-MM-DD)

## 주요 활동

- 활동 이름 N건 (+A / -D 줄):
  - 세부 내용 하나
  - 세부 내용 하나
- 활동 이름 N건 (+A / -D 줄):
  - 세부 내용 하나

## 활동 요약

| 활동 | 건수 | 비율 | 변경 줄 (+/-) |
| --- | --- | --- | --- |
| 기능 개발 | 12 | 40% | +3,210 / -840 |

## 저장소별

| 저장소 | 공개 여부 | 건수 | 변경 줄 (+/-) |
| --- | --- | --- | --- |
| owner/repo | 비공개 | 18 | +2,900 / -700 |

## 기간별 추이

(기간이 한 달을 넘을 때만)

- 1월: 5건
- 2월: 8건

## PR 목록

### owner/repo

#### 기능 개발 (12건)

| 날짜 | PR | 변경 줄 (+/-) | 파일 |
| --- | --- | --- | --- |
| 09-03 | [PR 제목](링크) | +120 / -8 | 5 |
| 09-05 | [PR 제목](링크) | +40 / -2 | 3 |

#### 버그 수정 (6건)

| 날짜 | PR | 변경 줄 (+/-) | 파일 |
| --- | --- | --- | --- |
| ... | | | |

## 조회 정보

- 계정: USER
- 저장소: R개 (공개 a개 / 비공개 b개)
- 머지한 PR: N건 (종료일이 미래이면 "오늘 MM-DD까지"를 덧붙인다)
- 변경 규모: +A / -D 줄, 파일 F개
```

### 작성 규칙

- PR 목록은 표로 쓴다. 저장소를 대분류(`###`), 활동을 소분류(`####`)로 하고, 활동마다 표 하나를 둔다.
- 표 안의 PR은 머지 날짜 오름차순으로 쓴다. 저장소 이름은 대분류 제목에 있으므로 표에서 반복하지 않는다.
- 저장소는 건수가 많은 순, 저장소 안의 활동도 건수가 많은 순으로 정렬한다.
- 표가 아닌 목록(주요 활동, 기간별 추이, 조회 정보)은 항목을 불릿으로 분리한다. 쉼표나 `·`로 여러 항목을 한 줄에 길게 이어 붙이지 않는다.
- 불릿에 `:`가 들어가는 항목은 `:` 뒤를 줄바꿈해서 하위 불릿으로 나눠 쓴다. 하위 불릿 하나에는 내용 하나만 쓴다.
- 주요 활동: 전체에서 비중이 큰 활동 3~5개를 고른다. PR 제목의 공통 주제(예: 같은 scope나 기능 이름)로 묶고, 그 활동의 건수와 변경 줄을 붙인다. 제목에 없는 내용은 쓰지 않는다.
- 활동 요약은 건수가 많은 순으로 정렬하고, 항목별 건수의 합이 전체 건수와 일치해야 한다.
- 비율은 소수점 없이 반올림한다. 반올림 때문에 합이 100%가 아니면 그 사실을 한 줄로 밝힌다.

## 주의

- 숫자는 조회한 데이터에서 그대로 계산한다. 조회하지 않은 값을 추정하거나 채우지 않는다.
- 활동 분류는 PR 제목에 근거한 판단임을 결과에 한 줄로 밝힌다. 특정 PR의 분류가 애매하면 "기타"로 두고 임의로 해석하지 않는다.
- PR 본문이나 코드 변경 내용은 분류 근거로 쓰지 않는다. 사용자가 더 깊은 분석을 요청할 때만 읽는다.
- 머지된 PR이 없으면 빈 표를 만들지 말고 "이 기간에 머지한 PR이 없다"고 답한다.
- 조직에서 접근 권한(SSO 승인 등)이 없어 조회되지 않는 저장소가 있을 수 있다. 오류나 누락이 의심되면 결과 끝에 그 사실을 밝힌다.
